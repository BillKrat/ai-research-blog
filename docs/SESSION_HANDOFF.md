## Architecture direction (2026-09-20, Windows session): reconciling the `nquad-end-to-end-poc` vision with the JSONB Hybrid + N-Quads decision — Option B synthesis, schema-driven security metadata, and point-in-time reproducibility

**This entire entry is a mutually agreed direction reached through a genuine, extended brainstorming session — not a mandate and not set in stone.** In the user's own words (paraphrased): landing on a logical result here doesn't mean it's permanent; treating it as immutable would lock the project out of new and emerging architectural patterns, new product needs, and the user's and Claude's own later ideas. A future session disagreeing with something below should re-derive it through the same kind of reasoning recorded here, not silently override it and not treat it as untouchable either.

**Where this came from:** the user built a standalone POC — a separate repo, [`BillKrat/lms-poc-work`](https://github.com/BillKrat/lms-poc-work) (local path `poc/nquad-end-to-end-poc`, **not** part of this repo) — with a Copilot assist, to demonstrate a vision he's held since before any of this repo's own architecture decisions existed: a decoupled, generic, reusable, minimal-coding backend where a *user* (not a developer) can define an entity or field and immediately get a working form/grid, with no redeploy. Reviewing that POC (build clean, all 58 xunit tests passing as of 2026-09-20) surfaced an apparent conflict with the "JSONB Hybrid + W3C N-Quads" decision recorded further below (2026-09-18 entry) — the POC is pure in-memory N-Quads, no JSONB half, no Postgres, one hardcoded graph. Working through *why* they seemed to disagree turned into the design session this entry records. Key POC files referenced below, pinned to commit [`522174b`](https://github.com/BillKrat/lms-poc-work/commit/522174b): [`DalBase.cs`](https://github.com/BillKrat/lms-poc-work/blob/522174b/src/Poc/DalBase.cs), [`UserDal.cs`](https://github.com/BillKrat/lms-poc-work/blob/522174b/src/Poc/UserDal.cs), [`UserBll.cs`](https://github.com/BillKrat/lms-poc-work/blob/522174b/src/Poc/UserBll.cs), [`EntitySchema.cs`](https://github.com/BillKrat/lms-poc-work/blob/522174b/src/Poc/EntitySchema.cs), [`app-screen.html`](https://github.com/BillKrat/lms-poc-work/blob/522174b/src/Poc.Angular/src/app/app-screen.html).

**Decision 1 — Option B, refined: the axis that matters is "does a human have to write and deploy a class before this entity can exist," not "generic vs. typed."** Two options were weighed. *Option A (rejected):* a single fully-generic engine with zero per-entity code, ever, including for User/security entities — rejected because it means encoding real business/security invariants (login rules, delete-protection, permission checks) as schema-driven config/rules data instead of reviewable code, which is a bigger, less trustworthy undertaking than a data layer, and the wrong place to carry that risk. *Option B (chosen):* the POC's own `DalBase<TEntity>`/`UserBll` already show that ~95% of a real Dal/Bll is mechanical and entity-agnostic (CRUDL, audit writing, the Add/Edit/Delete/Undo/Save/Previous/Next state machine) — the *only* genuinely User-specific logic in the whole POC is one guard rule (`CanDelete` refusing to delete the current user) and one hardcoded formatting special case (the `mailto:` prefix on Email in `UserDal.BuildQuadruples`/`Materialize`). So: extract the generic 95% into a `GenericDal<TEntity>`/`GenericBll<TEntity>` (not yet built anywhere, POC or here). Product-defined and security-critical entities (User, credentials, tokens) get a thin, named, versioned subclass (`UserDal : GenericDal<User>`, `UserBll : GenericBll<User>`) that pins a specific schema IRI at compile time and overrides only the handful of real business rules — giving DI a concrete, code-reviewed, NuGet-versionable type, consistent with the existing `Adventures.*` extraction convention (see the 2026-09-19 extraction decision further below). Tenant/user-authored entities — created at runtime through a schema editor that doesn't exist yet — are served directly by the generic engine with **no subclass at all**, because by construction no developer could have written one in advance. This is the mechanism that makes "a tenant defines a new entity, a form and grid appear immediately" literally true rather than aspirational.

**Fix required before Option B holds up:** the `mailto:` prefix hardcoded into `UserDal` is exactly the kind of per-field formatting rule that breaks once a tenant-authored entity needs the same capability with no subclass available to hardcode it into. It needs to become schema-declared metadata (something like a `valuePrefix` property on the field), enforced generically — not fixed for User only.

**Decision 2 — new field-level schema metadata, none of it built yet (POC only has `fieldType`/`predicate`/`isRequired` today, see `EntitySchema.cs` above):**
- `encrypted` (bool) and `searchable` (bool) — drive the PHI/PII encryption design below.
- A role/permission requirement per field — drives "nothing crosses the wire the caller isn't entitled to," below.
- `version` — which schema version a given quad set was written under (ties into Decision 4).
- A value-transform property replacing the hardcoded `mailto:` case above.

**Decision 3 — PHI/PII fields get two independent stored representations, not one, and search rides on the second one:** a **vault value** (AES-256-GCM, random nonce per write, reversible, decrypted only for display) and, only for fields also marked `searchable`, a separate **search value** (HMAC-SHA256 of the *normalized* plaintext — lowercased/trimmed for email, canonicalized to one format for phone numbers, or semantically-identical values silently fail to match — one-way/non-invertible, keyed by a value *derived separately* from the vault key via HKDF with a distinct purpose label, never the vault key itself). A single merged deterministic ciphertext serving both roles was considered and rejected: it would mean anyone who exfiltrates the table gets a permanent equality/frequency map across every searchable PHI field, for free, forever, since the "searchable" property and the "stored" property would be the same bytes. Splitting the keys means a compromised search key only yields an equality oracle (confirm/deny a guessed value) — never decryption of actual content — while a compromised vault key is a separate, independent failure with its own blast radius. **Important nuance for whoever builds this:** the search value's one-wayness stops mathematical inversion of the hash, not an offline dictionary attack — if the search key leaks and an attacker has a plausible candidate list (common email patterns, a breach corpus), they can still confirm guesses forward through the same HMAC. This is a real, live risk specific to PHI (unlike passwords, PHI values are low-entropy and guessable) — it's the reason the search key needs its own rotation/access discipline, not evidence the scheme is broken. Search is intentionally exact-match only, by explicit user requirement — no partial/fuzzy matching, no n-gram indexes. The search-value column/predicate needs a real index or this just relocates the existing O(n) scan problem (Decision 6) rather than solving it. Root/master key material must live outside the running application's own storage entirely (a real KMS/HSM/vault, never co-located with the data it protects) — which KMS/provider is still an open, unchosen implementation detail; a single env-held key is an acceptable placeholder for continued prototype work only.

**Decision 4 — Security/Identity schemas are structurally excluded from any tenant-facing schema editor.** Not a convention, a hard boundary: no tenant self-service schema-mutation path should ever be able to reach the definitions of credential, token, or M2M-secret schemas, regardless of how the generic engine's authoring UI ends up designed.

**Decision 5 — no field crosses the wire unless the current caller's role is entitled to it, enforced at materialization, never after.** Role/permission-based field filtering happens inside `GenericDal`/`GenericBll`, driven by the per-field role metadata from Decision 2, *before* a `DynamicEntity` is even built — not filtered afterward in an API serializer or hidden by an Angular template. Rationale, stated directly by the user: relying on presentation-layer hiding means the full, unredacted payload still existed in a server-side response object at some point, inspectable by anyone reading raw HTTP traffic (Fiddler, browser devtools) regardless of what the UI chooses to render.

**Decision 6 — point-in-time reproducibility: two independent versioning axes, and only one of them is ever replayable.** Origin: the user's own past experience on a project, where a later release's changed BLL rendering logic altered how previously-approved data displayed, with no way to reconstruct what had actually been shown/approved except a hard-copy printout — flagged as a real gap worth closing here too, not hypothetically. The existing audit trail (`AuditRecord`/`DalBase.WriteAudit`) does not cover this: it records *data* drift (field X changed from A to B), never *logic* drift (the same field values, reinterpreted by different code, rendering differently) — from the data's point of view in a logic-drift scenario, nothing happened, so nothing gets recorded.
- **Fidelity axis (versioned, replayable):** what a record looked like / how it was computed at approval time. Mechanism: `IUserBll` (and the equivalent per entity) gets multiple coexisting implementations registered via .NET keyed DI (`AddKeyedScoped`/`[FromKeyedServices]`, native since .NET 8), keyed by a version tag. A small resolver (not yet named or built — something like `IUserBllFactory`) reads the version stamped on the record itself and looks up the matching keyed implementation. **The version is never a value the caller/client supplies or selects** — accepting a client-supplied version would let a caller deliberately request an older, less-strict implementation as a downgrade attack; it must be read only from the record's own stored metadata.
- **Access axis (never versioned, always current):** the role/permission field filter from Decision 5 is a single, unversioned pass that wraps whichever version's output comes back, driven by *today's* permission metadata regardless of which historical rendering logic produced the underlying values. This was the one hole in the design the user said he would not have caught himself, so it's spelled out explicitly rather than folded into the bullet above: if permission filtering were part of the versioned/replayable Bll, replaying old logic would also replay old, possibly since-tightened, access rules — resurrecting a historical rendering could leak something current policy would redact. Access and fidelity must never share a version.
- **Scope, deliberately narrowed:** this machinery only ever activates for content that has actually passed through a freeze/approval event — draft/beta/live-editable content always runs on current logic (it only ever has one version, current), so none of this needs to exist for anything short of an approved record. Concretely scoped to **blogs and their associated uploaded documents**, not every entity in the system.
- **Term chosen: "Approved snapshot"** for the frozen/pinned state. "Published" was considered and rejected — already used elsewhere in the product's existing vocabulary, would overload an existing term.
- **Approved snapshot behavior:** viewing one is permanently locked to whatever version was stamped on it at freeze time, never a version the viewer selects. Editing an Approved snapshot is a one-way action — the user gets an explicit warning dialog before editing that they cannot return to the old version afterward — and always re-enters through the current version (with a migration step if the shape changed); a live, editable record does not go on drifting under old logic indefinitely, only a frozen Approved snapshot does, forever. Uploaded documents attached to an Approved snapshot need the same immutability guarantee as the entity's own fields, or the reproducibility promise has a hole nothing in the schema/quad layer would ever catch: **hash the file, store it addressed by that hash, and never allow a hash already referenced by an Approved snapshot to be overwritten** — replacing a document on an already-approved post goes through the same edit-creates-a-new-draft path as any other change, and the original Approved snapshot keeps pointing at the original file's hash forever. Viewing a historical Approved snapshot reconstruction is itself a sensitive read and should generate its own access-log entry (who viewed what, under which version, when), separate from `AuditRecord`'s data-change tracking. Not every code change warrants a new permanent version tag — only one that would alter the interpretation of *already-approved* output — deliberately left as a per-instance judgment call rather than a rigid rule ("we'll know when we do it," per the user); revisit if the version count starts growing without bound, which would be a sign the bar is being applied too loosely.

**Decision 7 (standing caveat, not new) — indexing at real scale.** `InMemoryQuadrupleStore.List().Where(...)`, used throughout the POC's `DalBase`/`EntitySchema`, is a full scan on every call — fine at POC scale (140 seed quads), and this is exactly why the POC intentionally stayed in-memory instead of sitting on the JSONB-hybrid Postgres schema from the 2026-09-18 entry below. Whenever any of the above actually gets built against that schema, both the base entity/triple lookups and the new PHI search-index column need real indexes (a subject/predicate composite index for triples, a b-tree on the search-index column) — this is the JSONB-hybrid's actual justification, not just a prior decision kept out of inertia: the boring, always-queried fields get indexed structure, the long tail of ad hoc/tenant-authored fields stays in triples.

**Explicitly not yet built — say so plainly, don't guess if picking this up later:**
- `GenericDal<TEntity>`/`GenericBll<TEntity>` don't exist anywhere. The POC still has hand-written `UserDal`/`UserBll` with the `mailto:` wart intact.
- No schema-authoring UI/API exists for tenants — schema still only loads from a pre-seeded quad file (POC) or hasn't been designed at all against this repo's JSONB-hybrid model.
- No encryption (vault or search value), no KMS integration, no role/permission field-visibility filtering, and no version-tagged keyed-DI Bll resolution exist anywhere in code — all of Decisions 3, 5, and 6 are design reached through this conversation, not implementation.
- Multi-tenant graph scoping (`"tenant:x/org:y/user:z"`, per the 2026-09-18 entry below) was never exercised by the POC — its seed data has tenants/orgs/blogs/roles sitting right next to User, but every quad uses one hardcoded default graph.
- KMS/key-management provider for the vault/search keys is unchosen.

## NEW DIRECTION (2026-09-19, Windows session): a bigger product vision surfaced — "BlogAI (new)", a developer-review tool — and it reshapes the planned MCP architecture. **Supersedes the "two separate MCP server processes" plan in "After auth: the MCP/agent work" further below.**

**The vision, in the user's own words (paraphrased, so a future session has the actual motivation, not just the resulting architecture):** in a world where AI writes an increasing share of code, a human developer can no longer keep up by reading every line — "we can comprehend and understand the code no more than we can the foundational classes of an SDK - we have to trust, but at the same time have a feasible means to review." The spinoff product concept: a corporation deploys "BlogAI (new)" and ties it to a repo. As AI writes code, the tool auto-generates review blogs (high-level concepts, a Mermaid sequence diagram, a code overview) explaining the current work — documentation that grows *with* the code, tagged with PBI/Task numbers, searchable, so a developer can comprehend and approve/modify AI-written work without digging into implementation detail. **This is a spinoff of `ai-research-blog`, not a replacement for it** - `ai-research-blog` remains the AI-starter-kit product; "BlogAI (new)" is a separate, related product idea this MCP architecture is now being shaped to support.

**Concrete demo of the concept, built this session:** [Login Path Autopsy](https://claude.ai/artifact/WuFQzaVGDYvFjjYxjesdYf) - a Claude Artifact (private to the user's account) reviewing this same session's real work (wiring `Adventures.Identity` into the WebApi, the two `Adventures.Data` bugs found/fixed - see the RESOLVED step-3 entry below) with a Mermaid sequence diagram of the actual login call graph. **Architecture decision this drives - `mcp.global-webnet.com` as a single, consolidated MCP Server, composed via MEF, not multiple separate deployable processes:**
- `api.global-webnet.com` (the existing `AiBlogResearch.WebApi`, MCP Host role - unchanged) calls a **new** `mcp.global-webnet.com` site/app-pool over machine-to-machine auth, using the client-credentials mechanism already built (`AiBlogResearch.Security`'s M2M work - see "Security / Auth" further below). This subdomain split maps cleanly onto this project's existing SmarterASP convention of one site = one app pool = one set of scoped FTP credentials (`billkrat-global`/`billkrat-api` today; a third scoped identity for `mcp` would follow the same pattern).
- Tool sets - PostgreSQL, SQL Server, FileSystem, and whatever comes later - are each their **own class-library project**, not baked into the MCP Server host. The host discovers and loads them via **MEF** (Managed Extensibility Framework), not a hardcoded `PackageReference`/DI registration per tool set.
- **Why MEF specifically, not just plain DI with a `ProjectReference` per tool set (the initially-proposed, simpler alternative):** the deciding requirement is that *third-party developers* should be able to write a new tool extension and drop the compiled assembly into a folder - no host rebuild, no access to this project's source - the same way `BlogAI`'s own `BlogEngine.Wiki` extension model already works for that legacy app (`BlogEngine.Core/Extensions.cs`, plus `BlogEngine.Wiki`'s hyperlink-extension mechanism, which the user has personally used to add cross-blog wiki-link behavior without touching `BlogEngine.Core`). Plain DI + `ProjectReference` would be simpler for tools *this* project writes itself, but doesn't give an outside developer that drop-in-a-DLL path at all. Don't revisit "just use DI" without this requirement changing.
- Each tool-set project's tests are written **TDD-style, with the test project standing in for the future MCP Server calling the tool** (not the future MCP Server's own code) - the MCP Server/host code and the MEF composition/loading mechanism itself are not being built yet in any of these tool-set projects.

**Verification method:** a throwaway console app (session scratchpad, never committed) built the exact real production classes by hand (`NpgsqlSqlExecutor`, `PostgresEntityRepository`, `PostgresUserCredentialStore`, `PasswordHasher`, `JwtTokenService`, `UserAccountService` - no fakes/mocks), pointed at the same `ConnectionStrings:Postgres` user-secret, then: seeded one throwaway user entity + `user_credentials` row, called `IUserAccountService.LoginAsync` with a wrong password (got `Succeeded=False, FailureReason=InvalidCredentials`), the correct password (got `Succeeded=True`, a real signed JWT, `MustChangePassword=True` from the schema's default), and an unknown username (same `InvalidCredentials` - confirms the deliberate non-enumeration behavior), then deleted the test entity (cascades to `user_credentials`) so nothing was left behind in the shared dev database. Re-ran this same script against the actual published nuget.org package (not a source reference) as the final check, not just during bug-fixing - see below.

**Bug #1 (blocked step 3 immediately): `Adventures.Data` 0.2.0's published nupkg tried to compile its own bundled `.sql` files as C#.** Adding the package reference failed the whole solution build with ~200 C# compiler errors pointing at `schema.sql`/`seed-tenant-admin.sql` inside the NuGet package cache. Root cause: `Adventures.Data.csproj`'s `<None Include="Sql\**\*.sql" ... PackagePath="contentFiles\any\any\Sql\" />` had a trailing separator that, combined with NuGet's implicit `%(RecursiveDir)` for a glob `Include`, produced a doubled `//` in the packed nuspec's `<files include>` glob (`any/any/Sql//schema.sql` instead of `any/any/Sql/schema.sql`) - so the nuspec's explicit `buildAction="None"` never actually matched the real packed file path, and NuGet fell back to inferring a build action for the unrecognized `.sql` extension, which defaults to `Compile`. Fixed in `Adventures.Foundation` (`src/Adventures.Data/Adventures.Data.csproj`) by giving the `None` item an explicit per-file `PackagePath` (`contentFiles\any\any\Sql\%(RecursiveDir)%(Filename)%(Extension)`, no trailing-separator ambiguity) plus `<PackageBuildAction>None</PackageBuildAction>` metadata - verified locally first (packed to a temp folder, consumed from a scratch project, clean build) before touching anything published. **Bug #2 (found immediately after bug #1's fix, once the login path actually ran a query): Dapper couldn't materialize `Entity`/any record with a `DateTimeOffset` property against a real Postgres reader.** Every `IEntityRepository` call that queries rows (`GetAsync`, `FindByStandardFieldAsync`, `ListAsync`) threw `System.InvalidOperationException: A parameterless default constructor or one matching signature (...) is required for Adventures.Data.Entity materialization`. ## Data access layer (2026-09-18): JSONB Hybrid + W3C N-Quads, mocked TDD, not yet wired to the live Docker Postgres

**Decision:** the generic CRUDL data access layer that the future `McpServer.Database` will sit on top of is built as a new class library, `AiBlogResearch.Data` (`src/AiBlogResearch.Data/`), using a **JSONB Hybrid + W3C N-Quads** storage model rather than a conventional per-entity-type relational schema. Rationale: this is a blog system where users can design and populate their own custom data forms/grids, and can extend the application's own standard fields (user info, post fields, etc.) at a granular **tenant (domain) → org (blog) → user** level — a fixed relational schema can't absorb that kind of user-driven, per-tenant/org/user extensibility without constant migrations. The hybrid split:
- **`entities` table (JSONB side)** — one row per entity (`id`, `tenant`, `org`, `entity_type`, `standard_fields JSONB`, timestamps, `row_version`). This holds the app's own "standard" fields (whatever the app ships with, e.g. a post's title/body) as an indexable/queryable JSONB document — a GIN index is on the column. Structured, known-shape data belongs here.
- **`entity_triples` table (N-Quads side)** — W3C N-Quad style `(subject, predicate, object, object_datatype, graph)` statements, where `subject` is an `entities.id` foreign key and `graph` encodes the tenant/org/user scoping context (e.g. `"tenant:acme.com/org:my-blog/user:42"`). This is the mechanism for fully user-defined/ad hoc fields — a user designing their own form/grid adds arbitrary predicate/object statements without any schema change, and the `graph` value lets the same predicate mean something different (or simply be scoped differently) per tenant, per org, or per individual user.
- See [src/AiBlogResearch.Data/Sql/schema.sql](../src/AiBlogResearch.Data/Sql/schema.sql) for the actual DDL (apply manually against the local Docker Postgres container — no migration tool wired up yet).

**Interfaces (generic, not tied to any one entity type):** `IEntityRepository` (`CreateAsync`/`GetAsync`/`UpdateAsync`/`DeleteAsync`/`ListAsync` — the CRUDL side, backed by `entities`) and `ITripleStore` (`AddTripleAsync`/`GetTriplesAsync`/`RemoveTripleAsync` — the extension-field side, backed by `entity_triples`), implemented by `PostgresEntityRepository` and `PostgresTripleStore` respectively. Both route all SQL through a small `ISqlExecutor` seam (real implementation: `NpgsqlSqlExecutor`, using Npgsql + Dapper) — this is what made the repositories unit-testable without a live database.

**TDD approach — mocked, not integration-tested yet:** the user has a local Docker Postgres container running, empty, for this project — but this pass deliberately did **not** connect to it. Instead, `test/AiBlogResearch.Data.Tests` uses a hand-rolled `FakeSqlExecutor` (matching this project's existing convention of hand-written test doubles over a mocking library like Moq — none is referenced yet) to verify `PostgresEntityRepository`/`PostgresTripleStore` orchestration logic (SQL shape, parameter passing, affected-row semantics, null-argument guards) in isolation. 16 tests, all passing. **Next step when picking this up again:** apply `schema.sql` to the Docker container and add a real integration-test pass (or a small console/manual smoke test) that exercises `NpgsqlSqlExecutor` end-to-end — nothing has touched the live database yet.

## Users, credential vault, and tenant-admin seeding (2026-09-18) — extends the data access layer above

**Design goal, stated by the user:** once a user authenticates, credentials must never be passed around again — only the user's UUID travels between the WebApi/MCP Host and MCP servers (the `sub` claim in the JWT). An MCP server that needs to check permissions or fetch profile data looks the UUID up itself against a "vault" it (or the auth service) controls; it never receives a password or secret directly. This is the same "MCP doesn't pass credentials around" principle as the M2M client-credentials work above, applied to human users.

**What was added, in `src/AiBlogResearch.Data/Sql/`:**
- **`schema-users.sql`** — a user is just another `entities` row (`entity_type = 'user'`); nothing new was invented for "where does a user live," the existing JSONB Hybrid + N-Quads model already covers it. **Standard user fields** (kept deliberately minimal, since the N-Quads triples mechanism already exists for anything beyond this) live in `entities.standard_fields` JSONB:
  - `username` — unique login name within the tenant
  - `email`
  - `display_name`
  - `status` — `active` | `disabled` | `must_change_password`
  - `roles` — text array, e.g. `["TenantAdmin", "Author"]`, drives which scopes/claims get issued at login
  - A partial index on `standard_fields ->> 'username'` (filtered to `entity_type = 'user'`) makes tenant/username login lookups fast without scanning JSONB broadly.
  - A separate **`user_credentials`** table (the "vault") holds `password_hash`, `password_algorithm`, `must_change_password`, lockout state, and login timestamps — keyed 1:1 on `entities.id`. **Only the auth/security service ever reads this table.** MCP servers and all other callers only ever see the `entities.id` UUID.
- **`seed-tenant-admin.sql`** — seeds one `Admin`/`Password` user per new tenant/org being initialized, mirroring BlogEngine.NET's own convention (a deliberately simple default that the admin is expected/forced to change immediately). `must_change_password = true` is set on the seeded row specifically so this is not a standing security hole — it forces rotation on first login. The password hash in the script is a **placeholder that must be replaced** with the real output of `PasswordHasher.Hash("Password")` before use; it is not a usable hash as checked in.

**Why user passwords get a different hasher than M2M client secrets — this is the one place this session made a hard security-over-convenience call:**
- `AiBlogResearch.Security` already had `IClientSecretHasher`/`ClientSecretHasher` (single-round salted SHA-256) for M2M client secrets — appropriate there because those secrets are high-entropy, machine-generated values, not guessable, so a fast hash is fine.
- Human passwords are the opposite: low-entropy, dictionary-guessable, chosen by a person. Reusing the fast M2M hasher for passwords would make offline brute-force/dictionary attacks against a stolen `user_credentials` table dramatically cheaper. **The user's explicit instruction was: security must always win over convenience/expedience when the two are in tension — this rule was applied literally here rather than reusing the existing hasher to save a step.**
- New **`IPasswordHasher`/`PasswordHasher`** (`src/AiBlogResearch.Security/`) was added instead: PBKDF2-HMAC-SHA256, 210,000 iterations (the OWASP 2023 minimum recommendation for that algorithm), random 16-byte salt per password, stored as `"{iterations}:{saltBase64}:{hashBase64}"`. The iteration count is embedded in the stored hash (not hard-coded at verify time) specifically so a future increase to the iteration count doesn't invalidate/break verification of already-stored hashes — old and new hashes can coexist and both verify correctly.
- Registered via `AddSharedJwtAuthentication` in `JwtServiceCollectionExtensions.cs`, so any host that already wires up JWT auth gets `IPasswordHasher` for free, no separate registration call needed.
- 13 new unit tests in `test/AiBlogResearch.Security.Tests/PasswordHasherTests.cs`, all passing (51 total in that project now). No mocking library used, consistent with the rest of this codebase.

**Explicitly deferred / not yet built (say so plainly, don't guess if picking this up later):**
- No C# repository/service code yet reads or writes `user_credentials` or the `roles`/`status` JSONB fields — only the SQL schema, the seed script, and the password hasher exist so far. The next piece would be a `IUserAccountService` (or similar) in `AiBlogResearch.Security` or a new small library, composing `IEntityRepository` + a credential-vault-specific data access class, to actually perform login (verify password, check lockout, issue JWT with `roles`-derived scopes).
- No tenant-bootstrap tool/endpoint exists yet to actually run `seed-tenant-admin.sql` with a real generated hash — right now it's a manual script requiring a human to paste in `PasswordHasher.Hash("Password")`'s output. A small console command or bootstrap-only WebApi endpoint would remove that manual step.
- `pgcrypto` (needed for `gen_random_uuid()` in the seed script) has not been confirmed as enabled on the actual Docker Postgres container — check `CREATE EXTENSION IF NOT EXISTS pgcrypto;` runs cleanly before relying on the seed script.

## Security / Auth — **superseded 2026-09-18: custom JWT service, not Auth0**

**Decision reversed again (2026-09-18):** the Auth0 decision below (2026-09-14) was never implemented and has been overridden. Initial framing was "Auth0 is extreme overkill" for this project's needs; the concrete, decisive reason surfaced once the user actually reset/reconfigured their Auth0 account to evaluate it fresh: **Auth0's free tier allows 25,000 monthly active users (very reasonable) but only 1,000 machine-to-machine token requests per month.** This project's design has **two MCP servers (PostgreSQL query, File Search) that are mainstream, high-frequency call paths** — searching uploaded content and blog content, and querying Postgres, are the app's core features, not occasional admin operations — so 1,000 M2M requests/month would be exhausted almost immediately under real usage, forcing an upgrade just to run the app as designed. Since `ai-research-blog` is explicitly an **AI starter kit** meant to stay cheap/learnable for developers standing up their own AI-assisted research/blog system (not a funded product), baking foundational security into a vendor whose free tier can't sustain the app's own core request volume was judged an unreasonable constraint on the project's own audience — a self-hosted JWT-issuing security service was built instead, as a reusable `AiBlogResearch.Security` class library shared by `AiBlogResearch.WebApi` (as both issuer and validator). No external IdP is used. **This is a permanent architectural decision for this reference project, not a stopgap** — see the full M2M cost analysis further below in "After auth: the MCP/agent work" for the resolved TODO this traces back to. Documented here so no future session re-litigates or re-introduces Auth0 based on the stale text further below.

**What actually shipped:**
- `AiBlogResearch.Security` (class library, `src/AiBlogResearch.Security/`) — `JwtTokenOptions` (Issuer/Audience/SigningKey/AccessTokenLifetime, bound from the `Jwt` config section), `IJwtTokenService`/`JwtTokenService` (HMAC-SHA256 signed tokens; `IssueToken` for user logins, `IssueClientToken` for M2M with a `scope` claim), and `AddSharedJwtAuthentication(configuration)` — the one DI extension both a user-auth host and any future MCP server would call to register JWT bearer validation against the same issuer/audience/signing key.
- `AuthController` (`POST /api/auth/token`, `GET /api/auth/whoami`) — user login is currently a single config-seeded demo user (`DemoUser:UserName`/`DemoUser:Password` in user-secrets) — a placeholder to replace with a real user store (DB/ASP.NET Identity) before production use; the token contract (`IJwtTokenService`) doesn't need to change when that happens.
- Signing key and demo credentials are stored via `dotnet user-secrets` locally (never committed); production should use an environment variable or secret store instead.
- Full TDD coverage in `test/AiBlogResearch.Security.Tests` and `test/AiBlogResearch.WebApi.Tests` (xUnit) — run via Visual Studio Test Explorer or `dotnet test`.

**Machine-to-machine (M2M) auth extension (2026-09-18), for the MCP Host ↔ MCP Server design further below:** OAuth2 **Client Credentials Grant**, built entirely on the same `AiBlogResearch.Security` foundation — no Auth0/external IdP needed for this either.
- `IClientCredentialStore` (client_id → hashed secret + allowed scopes) with an `InMemoryClientCredentialStore` implementation seeded from the `M2MClients` config section (non-secret `ClientId`/`Scopes` in `appsettings.json`, secrets seeded via user-secrets) — a DB-backed implementation is expected to replace this later behind the same interface.
- `IClientSecretHasher`/`ClientSecretHasher` — salted SHA-256 + constant-time comparison; secrets are never compared or stored in plaintext, even in the in-memory store. (Note: fine for high-entropy generated client secrets; a user-facing password store should use a slower KDF like PBKDF2/Argon2 instead.)
- `IJwtTokenService.IssueClientToken(clientId, scopes)` — issues a token with the client_id as subject and a standard space-delimited `scope` claim.
- `ScopeRequirement`/`ScopeAuthorizationHandler` + `AddScopeAuthorization(scopes...)` — registers one authorization policy per scope (named via `JwtServiceCollectionExtensions.ScopePolicyName(scope)`, e.g. `"Scope:mcp.postgres.query"`), so a future MCP server endpoint can be protected with `[Authorize(Policy = JwtServiceCollectionExtensions.ScopePolicyName("mcp.postgres.query"))]`.
- `M2MAuthController` (`POST /api/auth/m2m/token`) — validates `client_id`/`client_secret`, grants the intersection of requested and allowed scopes (or all allowed scopes if none requested), returns 401 for unknown clients, wrong secrets, or scopes outside what the client is allowed.
- Seeded demo clients (config in `appsettings.json`, secrets in user-secrets): `mcp-host` (both scopes), `mcp-server-postgres` (`mcp.postgres.query` only), `mcp-server-filesearch` (`mcp.filesearch.search` only) — placeholders for when the real MCP servers are built (see "After auth" section below); no MCP server projects exist yet, this session only built the security foundation they'll depend on.

**Superseded content below (2026-09-14 Auth0 decision) — kept for history, do not act on it:**

**Decision (2026-09-14, reversed from the initial "build our own minimal Auth0-style service" idea):** use the user's existing Auth0 account rather than rolling custom auth. Reasoning, for anyone tempted to re-litigate this: auth is adversarial in a way the rest of this stack isn't — a subtle bug in a hand-rolled token/session/password-reset flow is catastrophic (account takeover, breach) in a way a subtle bug in the Angular UI or WebApi just isn't, and "minimal scale" doesn't mean "minimal risk" here. The goal for our integration is simply to avoid that class of problem — a clean, deterministic login flow with no visible hang state. **Nothing fancy required, just clean and functional.**

## Why not Blazor / Python (don't re-litigate without new evidence)

- **Blazor** was ruled out: same single-vendor-risk pattern as Silverlight/WPF/UWP (all Microsoft-controlled client frameworks Microsoft later deprioritized), with a much smaller community than Angular/React and no foundation backing.
- **Gemini CLI** (Google) was reviewed as a case study: 107k GitHub stars and Apache 2.0 license did *not* protect it from being redirected into a closed-source successor (Antigravity CLI) with a ~98% free-quota cut — proof that star count/open license alone isn't a safety signal against single-vendor control.
- **MCP itself** is *not* single-vendor risk: Anthropic donated MCP to the Linux Foundation's Agentic AI Foundation (2025-12-09), co-founded with Block and OpenAI, Microsoft/Google/AWS/Cloudflare/Bloomberg also participating. The C# SDK is Tier 1 (same as TypeScript/Python), with a published, mechanically-enforced tiering system (conformance tests, auto-relegation) — not just a vendor's promise.
- **Angular** clears the vendor-risk bar Blazor doesn't: compiles to portable static JS with no backend dependency, MIT-licensed, and has a near-decade track record of low-pain major-version upgrades via `ng update` (unlike the AngularJS→Angular jump).
- Full reasoning trail is in this session's transcript if ever needed, but the conclusions above are the ones to build from.

**Machine-to-machine auth for WebApi → MCP Server calls — resolved 2026-09-18: custom JWT (client-credentials), not Auth0, and the reason is cost, not capability.** The `- [ ] TODO` below (checking Auth0's free-tier M2M quota) was resolved by actually checking: **Auth0's free tier permits 25,000 monthly active users (very reasonable for this project) but only 1,000 machine-to-machine token requests per month.** That M2M cap is the specific constraint that killed Auth0 for this design, not the user-auth side: this project's architecture calls for **two MCP servers (PostgreSQL, File Search) that are mainstream, high-frequency call paths** — every blog/file-content search and every database query the app serves routes through an M2M-authenticated call to one of them. 1,000 requests/month is not "occasional service call" territory here, it's the *core request volume* of a working app; it would be exhausted almost immediately by anyone actually using (or load-testing) the search features this project exists to demonstrate.

**Why this matters beyond just this project's own usage:** `ai-research-blog` is explicitly meant to be an **AI starter kit** — a learning/reference project for other developers standing up their own AI-assisted research/blog system, not a funded product with an ops budget. Baking foundational security into a vendor whose free tier can't sustain the app's own core usage pattern would force every developer who clones this kit to either hit the quota wall or pay to upgrade just to run the reference app as designed — the opposite of "keep cost near zero for someone learning this stack." For an actual funded company building a real product, Auth0's M2M pricing past the free tier is a completely reasonable cost of doing business (this is not a knock on Auth0 as a product) — it's specifically wrong *for this project's stated purpose*. **Decision: `AiBlogResearch.Security`'s custom JWT + OAuth2 client-credentials implementation (already built — see "Security / Auth" at the top of this doc) is the permanent M2M mechanism for this project, not a stopgap to migrate off of once Auth0's user-auth side is wired up.** Auth0 (or any external IdP) remains an option a developer forking this project could swap in later for their own deployment, but it is not the path this reference project itself takes.
