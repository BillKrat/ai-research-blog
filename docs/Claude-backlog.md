## Observability (priority)

- **CorrelationId end to end.** One id per process/request, carried through logs, outbound HTTP calls, the exception log and the error response. Plan: a Claude-decision doc (next step).
- **Exception signature.** Hash the exception (type, message shape, top app frames) so a repeat reuses its existing exception id and only the occurrence is logged.
- **MCP diagnostics tool.** DONE (2026-10-20): REST routes plus the MCP wire protocol at `POST /mcp` on the mcp site (initialize, tools/list, tools/call: diagnose_request, recent_exceptions, exception_signatures; scope `mcp.diagnostics.read`). Remaining: the human registers the endpoint in a Claude client and sets the client secret.
- **Health check detail.** `/api/health` reports each dependency (database, mcp) separately with timings.

- **No silent errors audit (from the human, 2026-10-18).** DONE (2026-10-20): dependency probes, signed-in and anonymous browser errors (caps), startup crashes and process-level failures (failure journal, reported on the next start), unobserved task failures, `ObservedBackgroundService` for future workers. Deliberately not done: (3) handled 4xx counter (a 4xx is the system working; revisit if abuse shows up) and (4) deploy smoke tests in the app (the GitHub workflow is their home). McpServer has no exception store, so it only logs.
- **Diagnose button (from the human, 2026-10-18): first version built 2026-10-19 (see the stage review); keep adding a rule per exception we meet; later an optional AI call (needs an API key and a data decision).** Original idea: when the diagnostics are mature, a Diagnose action on an exception or signature that runs a triage process and reports a verdict: gather the request's log lines and exceptions by CorrelationId (`IDiagnosticsReader`), check the dependencies involved (health probe, TLS, database), compare with earlier occurrences of the same signature, and propose a cause and next step. Starts as the read-only checklist a human or Claude follows; automate each step as it proves reliable.
- **Admin dashboard.** Status actions DONE (2026-10-20: Acknowledged / Fixed per kind, Regressed set by the system). Still open: move the exceptions area onto a Dashboard with signatures counted per day and links from a signature to its occurrences.
- **Performance thresholds and alerts (from the human, 2026-10-20).** Let an administrator set thresholds for performance (for example the p95 duration of an API endpoint, a database or N-Quad store query, an outbound call such as mcp or Anthropic, or a store round-trip count per request); when one is exceeded a warning icon shows (the same header icon family as exceptions) and we are alerted. Each alert then has two outcomes: raise the threshold (an informed decision, recorded) or look for an improvement. Particularly important because entities live in the N-Quad store, where one logical read is several quad queries and cost grows with data. Ideas to start from: time every request and store call with the CorrelationId already carried (the timings the health check and "responded in N ms" log lines already have); keep rolling percentiles per endpoint and per store operation; thresholds as configuration the admin edits on the Dashboard; a breach is recorded like an exception (throttled, with a signature and Acknowledged/Fixed status) so Diagnose and the MCP tool see it; count store calls per request to catch N+1 early (`NQuadEntityRepositoryListCostTests` pins this for one path). Needs a decision on storage of the measurements (in memory vs the store) and on how we are alerted (icon only, or e-mail/push).

## Features

- **Admin shell ported from BlogAI (direction from the human, 2026-10-20).** BlogEngine's admin (AngularJS, left menu: Dashboard, Content, Custom, Users, Settings, About; Users has Profile, Roles, Users, Contacts) is the model for the new admin. Build it in agile slices on the form/grid/relations contract, not as one port: start with Content > Posts and Pages (Pages first needs the Page-editor review recorded in the server-driven-forms decision), then the other Content items, Users (Users and Roles is form-contract stage 3), Settings as they are needed. At some point a server-supplied menu model (links, permissions) replaces hardcoded navigation, so the Angular admin menu is data from the API like everything else. Before each slice, review the matching BlogAI screen in the live admin (read-only, the human's signed-in browser) and port behaviour, not code.
- **Richer typed controls (from the human, 2026-10-20).** Stage 1 already picks a native control from the type (date input, checkbox, number input, text). Upgrade to Material controls chosen the same way, from the type the schema declares: a Material date picker for `Date`, a date-time picker for `DateTime`/`DateTimeOffset` (time zone shown, UTC stored), a slide toggle or checkbox for `Bool` (configurable per field), a number field with step/min/max from schema metadata, a select for fields with `options` or a `ref:` lookup (stage 3), masked inputs for phone/e-mail via the value prefix. The mapping stays in one place (`EntityForm.kindOf`) and the server stays the only authority on what a type means; per-field overrides can come as optional schema quads (like label and order).
- Form-contract stage 1 to 3, password-change caption and "Update password", Admin menu for the exception icon, per-field messages, targeted schema read at startup (see `AGENTS.md` Remaining).
